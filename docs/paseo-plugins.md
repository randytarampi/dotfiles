# Paseo community plugins

This owner-gated reconciler manages the registry IDs in `scripts/install-paseo-plugins.py`. Paseo JSON lists runtime IDs separately from `installation.identity.registry.id`; planning compares registry IDs, while enable/remove operations use the runtime ID. Unlisted plugins are reported and retained by default; `--prune` explicitly removes their Paseo configuration. A failed install, enable or remove is reported by name and does not abort the remaining operations; the run then exits nonzero.

Plugin compatibility floors are evaluated against the **running daemon** version from `paseo status --json`, not the CLI binary. After a Paseo upgrade the daemon can lag the CLI until it restarts, and the daemon is what rejects an incompatible install. The current floors are Node >=22.18 for `stevecastaneda/progress`, a verified `codexbar` on the daemon PATH for `uiyzzi/codexbar-usage`, Paseo 0.8–0.13 and macOS for `dutchakdev/machine-status`, Node >=24 plus Paseo >=0.13 for `omercnet/shared-browser`, and the registry-declared Paseo >=0.16.2 for `asherlc/devices` and >=0.16.1 for `asherlc/cheapskate`. Skipped entries print their reason; prerequisites are not guessed beyond documented or registry-reported floors.

Preview with `python3 scripts/install-paseo-plugins.py --dry-run`. Actual mutation requires both `--apply` and `DOTFILES_RUN_PASEO_PLUGINS_SETUP=1`. Plugin code runs unsandboxed in the Paseo daemon.

The shared-browser Chromium resolver checks the standard Chromium executable locations for macOS (`/Applications/Chromium.app/Contents/MacOS/Chromium`, the Homebrew `ungoogled-chromium` cask), Windows (`%LOCALAPPDATA%`/`%PROGRAMFILES%` Chromium installs and `chrome` on PATH, matching the winget `eloston.ungoogled-chromium` package) and Linux (`/usr/bin/chromium`, excluding Snap). `PASEO_SHARED_BROWSER_CHROMIUM_EXECUTABLE` must be an absolute path to the executable, not an app bundle.

The variable reaches the plugin through the **daemon** environment, and the plugin's `prepare:runtime` install hook runs inside the daemon, not in this script's subprocess. Setting it only for the installer therefore does not stop the bundled Chrome-for-Testing download on a host whose daemon lacks it; an observed 0.16.0 install staged its own browser despite the override. On macOS the script maintains a marker-delimited export in an existing recognizable `~/.paseo/launchd-daemon.sh` wrapper and requests `launchctl setenv`; it never creates a missing wrapper. Linux writes `~/.config/environment.d/90-paseo-shared-browser.conf`; Windows uses user-scoped `setx`.

`omercnet/context-mode` is owned by the Context Mode gate: it is installed and enabled only while `DOTFILES_RUN_CONTEXT_MODE_SETUP=1`, and skipped with that gate name as the reason otherwise. When it is eligible, the reconciler also points it at the repository-managed Context Mode CLI by writing `binaryPath` into Paseo's plugin settings at `~/.paseo/plugin-settings/context-mode/context-mode.json` (`{"version": 2, "values": {...}}`, owner-only, other values preserved), then reloads the plugin. A resolved binary under `~/.paseo/plugins/` is the plugin's own bundled runtime and is rejected rather than selected; the npm global the dotfiles manage is used instead.

A daemon restart is required to consume the persisted environment and to reach a newer daemon version; this script does not restart it and does not claim a running daemon picked either up. Until then the staged runtime browser remains the fallback. Verify installed state with `paseo plugin ls --json`. The installer redacts plugin subprocess output because it may contain private paths.
