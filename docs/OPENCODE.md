# OpenCode


Optional credentialed direct inference providers are described in
[OPTIONAL_INFERENCE.md](OPTIONAL_INFERENCE.md). They are not automatically
classified as free or included in strict-free fallback chains.

## Web Service

The LaunchAgent runs OpenCode v2 with `opencode serve`; its managed lifecycle is
available through `opencode service start|stop|status` and its registry stores
the service URL and password file. The web GUI is an SPA catch-all, so legacy
`/health` paths returning HTML are not health evidence. Use authenticated
`GET /api/info` (HTTP Basic, default username `opencode`, JSON ServerInfo).
Set `OPENCODE_PASSWORD` or, as fallback, `OPENCODE_SERVER_PASSWORD`; never log
the password. `OPENCODE_SERVER_PORT` selects the web port (default 4096).
Random `--port` in multiplexer aliases remains until ACP delegate flows are
validated.

OpenCode is the primary AI agent tool in this setup. Its configuration is
generated by `scripts/configure-opencode.py`, and its tiers are defined in
`configs/opencode/oh-my-opencode-slim.json`; see [docs/TIERS.md](TIERS.md) for
the full tier reference.

## Provider Presets

The `free` and `omo-slim-opencode-zen-free` presets are dynamically composed
from fresh catalogue snapshots and route evidence when generated. Selection is
fail-closed: missing, stale, malformed or unqualified evidence refuses the
selection rather than silently substituting a paid route. These checks establish
catalogue and configured-route provenance, not request-time billing, entitlement,
privacy or a guarantee of zero cost. No live availability was verified by this
documentation update. See [docs/TIERS.md](TIERS.md) and
[docs/LITELLM.md](LITELLM.md) for scope and remaining gaps.

### Temporary Disablement and Recovery

Generation refuses to publish an unqualified dynamic preset; it does not
automatically switch to a paid preset. Existing installed files are not
retroactively repaired until configuration is regenerated. Review the generated
selection and its provenance before use.

Catalogue availability and provenance are refreshed during generation; a
catalogue listing alone does not prove inference access. Do not treat generated
classification as runtime cost enforcement. Request-time admission, entitlement,
privacy and paid-route-spy evidence remain outside this mechanism (issue #87).

Four upstream-inspired preset families are represented in the shared registry:
[OpenAI](https://github.com/alvinunreal/oh-my-opencode-slim/blob/master/docs/presets/openai-preset.md),
[$30](https://github.com/alvinunreal/oh-my-opencode-slim/blob/master/docs/presets/thirty-dollars-preset.md),
[$40](https://github.com/alvinunreal/oh-my-opencode-slim/blob/master/docs/presets/forty-dollars-preset.md),
and [Zen Free](https://github.com/alvinunreal/oh-my-opencode-slim/tree/master/docs/presets).
The first three are selectable with the required provider credentials; Zen Free is
evidence-gated and may be withheld when fresh qualifying routes are unavailable.
Local deviations are documented in [docs/TIERS.md](TIERS.md):

| Preset | Providers | Observer | Fallback policy |
|--------|-----------|----------|-----------------|
| `omo-slim-openai` | OpenAI, with OpenCode Zen fallbacks | `openai/gpt-6-luna` | OpenCode Zen |
| `omo-slim-thirty-dollars` | OpenAI + GitHub Copilot | `openai/gpt-6-luna` | OpenCode Zen; Copilot designer may fall back to Zen Gemini |
| `omo-slim-forty-dollars` | OpenAI + Anthropic | `anthropic/claude-haiku-5-5` | Explicit OpenAI/Anthropic alternatives |
| `omo-slim-opencode-zen-free` (qualification required) | OpenCode Zen | `opencode/nemotron-3.5-super-vl-free` candidate | Empty fallback chains; selection fails closed without evidence |

All presets define an explicit observer. `image_routing: "auto"` routes image
attachments to the observer; the hook strips them from the main conversation
and saves them to disk, so orchestrators never receive image bytes.

OpenCode Zen uses the standard `OPENCODE_API_KEY` environment variable. The
alternative is `/connect`, which stores authentication in OpenCode's
`auth.json`; a key is not required for the generated provider block. GitHub
Copilot authentication uses the `/connect` GitHub device flow.

The current Zen free candidates are GLM-5.3 Flash for orchestration, DeepSeek
V4.1 Flash for design/fixing, and Nemotron 3.5 Super VL for observation.
These names alone do not demonstrate authenticated inference, image support,
or guaranteed zero cost. Earlier MiMo image probes failed or timed out;
Muse contributor routes may train on submitted prompts or images and are
not current defaults. Free-tier
IDs churn: `x-preview-f-free` and `hy3-free` were removed between 2026-08 and
2026-09.

## ACP Agent Verification

On OpenCode v2 the agent-facing server surface is `opencode acp` (stdio Agent
Client Protocol server; `--login` switches to auth login) — verified against
the v2.2.5 CLI (`opencode acp --help`). ACP adapters registered through the
repo's wrappers remain v1-process-compatible: external adapters keep their own
auth flows, and `opencode acp` exposes OpenCode itself as an ACP server to ACP
clients. Real delegate flows against the v2 binary are a machine-cutover
validation item (see the migration plan's PR D list); the multiplexer random
`--port` aliases stay until those flows pass.

ACP (Agent Client Protocol) agents are configured in `~/.config/opencode/acp-agents.json` (gitignored, generated by `scripts/configure-acp-agents.py`). To verify ACP agent setup:

1. **Check config**: `cat ~/.config/opencode/acp-agents.json` — should contain `acpAgents` with entries for configured agents
2. **Check merge**: ACP agents are merged into `oh-my-opencode-slim.json` during `configure-opencode.py` — verify with `grep acpAgents ~/.config/opencode/oh-my-opencode-slim.json`
3. **Restart OpenCode**: After any ACP config change, restart OpenCode for agents to load
4. **Authenticate**: Each ACP agent requires its own auth:
   - **Copilot**: `copilot auth`; the OpenCode provider uses `/connect`
   - **Cursor**: `cursor-agent login` (browser auth via Cursor account)
   - **Claude**: `claude /login` (claude-code-acp wraps claude)
   - **Codex**: OpenAI auth (codex-acp wraps codex)
   - **Gemini**: `GEMINI_API_KEY` env var or `gemini auth`
   - **Junie**: JetBrains IDE login
   - **Antigravity**: `agy auth login` (Google Sign-In via system keyring). Then enable the bridge: set `DOTFILES_RUN_ANTIGRAVITY_ACP_SETUP=1` and `make deploy`.
   - **Pi**: `pi-acp --terminal-login` for ACP registry auth. Uses `pi --mode rpc` internally. Set `PI_ACP_ENABLE_EMBEDDED_CONTEXT=true` for richer context. Gate: `DOTFILES_RUN_PI_SETUP=1`.
   - **Cortex**: Requires Snowflake account + `SNOWFLAKE.CORTEX_USER` role + `~/.snowflake/connections.toml` + `snow` CLI. Uses `cortex acp serve -c <CORTEX_CONNECTION>`. Gate: `DOTFILES_RUN_CORTEX_SETUP=1`. Graceful skip when no Snowflake connection.

5. **Local-fallback ACP agents**: `--local` variants use the combined local model pool across configured engines. Available: `@codex--local`, `@claude--local`, `@junie--local`, and `@pi--local` (cloud tiers only). `@pi--local` uses the full `~/.pi-local` configuration generated with `DOTFILES_LOCAL_FALLBACK_PRESET` (default: `local`) passed as `--preset`, rather than a single-model stub or `--local-fallback-preset` (which would retain the cloud default model). `@gemini--local` is emitted only when the winning engine is Gemini-compatible (Ollama today); non-Ollama winners are logged and skipped. `@copilot--local` is unsupported (no native Ollama). The winning engine supplies the endpoint for the pool-driven `--local` agent. These are auto-generated by `configure-acp-agents.py` — do not set manually.

6. **Test**: In OpenCode, use `/agent <agent-name>` to invoke a specific ACP agent (e.g., `@gemini hello`, `@copilot explain this code`, `@pi help`, `@codex--local review this`)

### Memory opt-in

`opencode-mem` is controlled by `DOTFILES_RUN_OPENCODE_MEMORY_SETUP=1` and
defaults to off. The managed `opencode-mem.jsonc` configuration uses loopback web hosting, local
embeddings, and pins memory extraction to the shared fast local LLM using
`opencodeProvider: "ollama"` and the bare `opencodeModel: "gemma4:12b-mxfp8"`
wire ID instead of inheriting the session's routing —
extraction is deterministic and offline-capable. Update the pin through the
model-update flow when the fast model changes. The plugin's own embedding
(`Xenova/nomic-embed-text-v1`) stays local and unchanged. Remote embedding endpoints
are deliberately absent and require an explicit egress decision.

## Observer Vision Path and Image Payloads

The OpenCode `@observer` lane routes through the LiteLLM proxy using the role
model from `DOTFILES_ROLE_MODELS` (e.g.
`observer=ollama/gemma4:12b-mxfp8`, bridged by
`scripts/configure-opencode-tier.py`). Requirements and observed practice as
of 2026-10-13:

- **Pillow is required in the LiteLLM venv** for Ollama image conversion.
  Without it, every image-bearing request to an `ollama/*` model fails with
  HTTP 500 ("ollama image conversion failed please run pip install Pillow"),
  and the model never sees the image. The proxy venv pins `Pillow==12.3.0`
  in `.chezmoiscripts/run_onchange_15-litellm.sh.tmpl`.
- **Proxy vision path validated (2026-10-13)**: a direct
  `/v1/chat/completions` probe through LiteLLM to
  `ollama/gemma4:12b-mxfp8` with an `image_url` payload transcribed a
  synthetic test image verbatim (text and shape colours correct). The
  Pillow pin plus the Ollama bridge are therefore healthy end to end.
- **Treat `@observer` image reports as unverified at OpenCode v1.19.0**:
  dispatching a single-image probe returned a plausible, well-formatted
  report whose content was hallucinated from the surrounding prompt — the
  image never reached the model — and a headless primary read stalled.
  Until this is fixed, corroboration rules apply: require verbatim strings
  from the payload in the report, or fall back to reading the image
  directly (orchestrator/`@observer`-independent probes).
- **Observe image payloads serially**: one image per `read` tool call and at
  most two images per `@observer` dispatch. Three-image payloads to
  `ollama/gemma4:12b-mxfp8` were observed to stall through the `ollama/`
  LiteLLM path (>180 s, no response); batch larger visual jobs across
  dispatches.
- **The final message must be the report**:
  `~/.config/opencode/oh-my-opencode-slim/observer_append.md` appends
  guardrails to the bundled observer prompt (verified in the installed
  OMO-Slim plugin source; per-agent append files load for all bundled
  agents on the next OpenCode run): complete plain-text report after the
  last read, never a pending or serialized tool call, state nothing as
  fact that was not seen in the payload, and partial success still emits
  observations plus an explicit error note. The file ships untracked —
  create it on new machines when the observer lane is in use.

> (v2-capable; the older "no v2 build" note no longer applies). Quota is

## Tokenscope

`@cheesecodestudio/opencode-tokenscope-v2` is an OpenCode plugin for analyzing
token usage and costs (replaces `@ramtinj95/opencode-tokenscope`):

- **Install**: `opencode plugin add @cheesecodestudio/opencode-tokenscope-v2@latest` (canonical plugin manifest; no `--global` under the v2 warm install flow)
- **Usage**: Token usage/cost surfaces in the TUI — the v2 package's exact command surface is unverified until machine validation; current docs carry the `/tokenscope` name forward
- **Config**: Added to the `plugins` array in `opencode.json` by `scripts/configure-opencode.py`
